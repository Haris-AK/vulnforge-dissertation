This chapter describes how VulnForge was designed, and implemented. The specification states what the system is required to do and the constraints that shaped the solution. The design then explains the main architectural decisions and the viewpoints needed to understand the platform: architecture, data model, challenge lifecycle, generation, verification, tutoring, and history. The implementation section describes how the most important design ideas were realised in the codebase, focusing on the parts that are critical to the system or that caused notable implementation problems.

\section{Specification}\label{sec:spec}

VulnForge has to solve three connected problems. First, it must provide a usable web interface where learners can create an account, store an SSH public key, choose a vulnerability category and difficulty, launch a challenge, submit a flag, and review previous attempts. Secondly, it must safely orchestrate infrastructure: create an isolated container, inject the learner's SSH key, apply an LLM-generated vulnerability specification, verify the result, and clean up afterwards. Thirdly, it must use generative AI in a constrained way so that an LLM can help create and tutor a challenge without being allowed to control the host directly or reveal the answer to the learner.

\subsection{Scope and assumptions}\label{sec:scope}

The system is designed for a controlled educational lab setting rather than for public Internet-scale deployment. A user interacts with VulnForge through a web dashboard and connects to the generated challenge environment through SSH. Each challenge environment is an Ubuntu 24.04 LXC container hosted on a Proxmox VE hypervisor. The container is intended to be ephemeral: it exists for one challenge attempt and is later destroyed because the challenge expires, is completed, or is manually ended.

The main operating assumptions are:
\begin{itemize}
	\item users authenticate through the VulnForge web application before launching challenges;
	\item each user stores an SSH public key in account settings before launching a challenge;
	\item learners connect to the challenge as a non-root Linux user called \lstinline|student|;
	\item the \lstinline|student| user has no normal administrative access, so any privilege gain must come from the generated vulnerability;
	\item each user may have at most one active challenge at a time;
	\item the platform stores the flag and solution summary server-side and does not expose them to the browser while the challenge is active;
	\item the vulnerable container is reachable through the intended lab network path, but the web application does not implement a full public VPN or network onboarding product.
\end{itemize}

These assumptions restrict the project scope. VulnForge does not attempt to implement payment, public cloud scaling, browser-based terminals, end-user Proxmox administration, or a complete managed VPN. The core purpose is to demonstrate controlled generation, deployment, verification, guided assistance, flag submission, and cleanup for short-lived vulnerable machines.

\section{Design}\label{sec:design}

The architecture of VulnForge uses a full-stack Next.js application as the control plane. It is connected to SQLite for persistent state, OpenRouter for LLM calls, Ansible for automation, and Proxmox VE for container lifecycle management.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.82\textheight,keepaspectratio]{figures/system_architecture.pdf}
	\caption{System architecture}
	\label{fig:system-architecture}
\end{figure}

The web application is the central authority. It validates user input, manages accounts and sessions, stores challenge state, invokes the LLM, invokes container orchestration, presents the challenge, and confirms completion. Students do not receive Proxmox credentials, Ansible inventory data, API tokens, flags, generated validation commands, or the private solution summary while a challenge is active.

Ansible is used as the infrastructure automation layer rather than embedding all Proxmox operations directly into the web application. This keeps the TypeScript code focused on workflow orchestration and leaves container operations visible as playbooks. The trade-off is that the web application must parse Ansible output, handle subprocess failures, and clean up when a playbook fails part-way through. This trade-off is acceptable because the project depends on repeatable infrastructure operations and because playbooks make the host-level actions easier to inspect and debug.

Proxmox LXC containers were chosen because they are lightweight, scriptable, and quick to create compared with full virtual machines. This matters because a challenge launch can already be delayed by LLM generation and verification. The limitation is that LXC containers are not as strong an isolation boundary as full VMs because they share the host kernel. For this prototype, unprivileged containers, a non-root learner account, short TTLs, and restricted generation policies are used to reduce risk. A production version would need stronger network and isolation controls.

\subsection{Data model}\label{sec:data_model}

The database contains four main entities: users, sessions, challenges, and messages.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.82\textheight,keepaspectratio]{figures/data_model.pdf}
	\caption{Database schema}
	\label{fig:db_schema}
\end{figure}

The \lstinline|challenges| table is the central domain object. It connects a database record to generated infrastructure by storing the Proxmox VMID, IP address, and hostname. It also stores user-facing metadata such as title, description, category, difficulty, hint, and attack vector. The \lstinline|flag| and \lstinline|solution_summary| fields are private fields used by the flag checker and tutor. Repository methods expose a public challenge object that omits these fields while the challenge is active.

Challenge state is represented by a \lstinline|status| field rather than only by the presence or absence of a completion timestamp.

\begin{table}[htbp]
	\centering
	\begin{tabular}{@{}>{\raggedright\arraybackslash}p{2.5cm}p{7cm}p{4.8cm}@{}}
		\toprule
		\textbf{Status}       & \textbf{Meaning}                                                           & \textbf{Set by}                                                               \\
		\midrule
		\lstinline|active|    & The user can work on the challenge and the container is expected to exist. & Challenge creation.                                                           \\
		\addlinespace
		\lstinline|completed| & The correct flag was submitted before expiry.                              & Flag submission route.                                                        \\
		\addlinespace
		\lstinline|destroyed| & The user manually ended the challenge.                                     & Challenge delete route.                                                       \\
		\addlinespace
		\lstinline|expired|   & The challenge exceeded its TTL.                                            & Active challenge checks, launch cleanup, or expired flag submission handling. \\

A partial unique index on \lstinline|challenges(user_id)| where \lstinline|status = 'active'| enforces the rule that a user can only have one active challenge. This is stronger than an application-only check because it still works if two launch requests race.

\subsection{Challenge lifecycle}\label{sec:lifecycle}

The challenge lifecycle is deliberately simple from the learner's perspective but requires careful implementation because database state and infrastructure state can become inconsistent.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.82\textheight,keepaspectratio]{figures/challenge_lifecycle.png}
	\caption{Challenge lifecycle}
	\label{fig:challenge_lifecycle}
\end{figure}

The application checks challenge status before chat requests, flag submissions, and deletion requests. Chat is only interactive for an active challenge, while history pages allow past messages to be viewed in read-only mode. Correct flag submissions are marked as \lstinline|completed|. Manual deletion marks the challenge as \lstinline|destroyed| immediately and then triggers container deletion asynchronously. Expiry is handled by application-side checks and by a host-side TTL reaper.

There is a deliberate separation between logical state and infrastructure state. The database may mark a challenge as destroyed before the Ansible destroy playbook has finished. Similarly, the TTL reaper may delete a container before the database is next checked. VulnForge accepts this eventual consistency because the main requirement is to stop users interacting with stale challenges and to prevent indefinite resource use. The design favours safe terminal state transitions and independent cleanup over a more complex distributed transaction between the database and Proxmox.

\subsection{Launch pipeline}\label{sec:launch_pipeline}

Challenge launch is the most complex workflow in the platform. It is exposed to the browser as a Server-Sent Events stream so that the UI can show progress during long-running stages.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.82\textheight,keepaspectratio]{figures/launch_generation.pdf}
	\caption{Launch pipeline}
	\label{fig:launch_pipeline}
\end{figure}

The pipeline has two verification levels. Normal launches run health-mode verification, which executes health checks and flag-protection checks. This catches common failures such as a web server not starting, a generated file missing, or the flag being directly readable by the learner. Full exploit verification is controlled by \lstinline|CHALLENGE_FULL_VERIFY_BEFORE_LAUNCH|. When this is enabled, the platform first deploys a disposable verifier container, injects the generated specification, runs exploit checks, destroys the verifier container, and only then deploys a fresh user-facing container.

This split is a deliberate design compromise. Full exploit verification gives stronger evidence that the generated challenge is solvable, but it is slower and can mutate the machine. For example, a privilege escalation exploit might change permissions, add files, or alter service state. Running such checks on the user's final container could partially solve or damage the challenge before the user begins. Health-mode verification is therefore used for normal launches, while full verification is reserved for evaluation or deployments where the extra delay is acceptable.

\subsection{Vulnerability generation design}\label{sec:vuln_gen_design}

The LLM does not directly control the infrastructure. Instead, it produces a structured \lstinline|VulnerabilitySpec| object that is treated as data.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.82\textheight,keepaspectratio]{figures/generation_policy.pdf}
	\caption{Generation and policy validation pipeline}
	\label{fig:generation_policy}
\end{figure}

The specification includes public challenge metadata, deployment instructions, private learning metadata, and private verification metadata. Listing~\ref{lst:vulnerability-spec-schema} shows an abbreviated version of the schema boundary.

\begin{listing}[htbp]
	\begin{minted}{TypeScript}
export const VulnerabilitySpecSchema = z.object({
  title: z.string(),
  description: z.string(),
  category: z.string(),
  difficulty: z.enum(["beginner", "intermediate", "advanced"]),
  hint: z.string(),
  apt_packages: z.array(AptPackageSchema),
  files: z.array(FileEntrySchema).min(1),
  services: z.array(ServiceSchema),
  setup_commands: z.array(z.string()).default([]),
  solution_summary: z.string(),
  attack_vector: z.string(),
  validation: ValidationSpecSchema,
});
	\end{minted}
	\caption{Abbreviated version of VulnerabilitySpecSchema}
	\label{lst:vulnerability-spec-schema}
\end{listing}

The choice to use structured output is central to the design. A free-text response from the LLM would be difficult to validate and dangerous to execute. A typed specification creates a contract between the model and the infrastructure pipeline. The rest of the system consumes files, packages, services, setup commands, and validation checks as structured fields rather than interpreting arbitrary natural language.

The design uses several safeguards:
\begin{enumerate}
	\item \textbf{Server-side flag generation.} The platform generates the flag as \lstinline|FLAG{...}| before calling the LLM. The model is instructed to embed this exact value somewhere reachable only through exploitation. This avoids relying on the model to invent a unique valid flag.
	\item \textbf{Structured output.} The Zod schema is converted to JSON Schema and sent to OpenRouter as a structured response format. The response is still parsed and validated again server-side.
	\item \textbf{Policy validation.} Schema validation checks structure, while policy validation checks semantic risks such as wrong category, wrong difficulty, missing flag, attempts to recreate the \lstinline|student| user, attempts to modify SSH configuration, unsafe paths, or unsafe validation commands.
	\item \textbf{Category-specific prompts.} Each vulnerability category has its own prompt and variants. This avoids one unmaintainable prompt file and gives each category clearer constraints.
	\item \textbf{Diversity mechanisms.} The prompt builder selects random variants and, for web categories, random application themes. It also passes previous challenges into the prompt as an exclusion list so that the model is instructed not to repeat previous scenarios.
	\item \textbf{Model fallback.} The OpenRouter integration can retry generation with fallback models when provider failures, empty responses, truncated responses, rate limits, or temporary server errors occur.
\end{enumerate}

\subsection{Verification design}\label{sec:verification_design}

Earlier versions of the system checked whether Ansible completed, but Ansible success alone does not prove that the generated challenge is usable. A web service may start but serve the wrong page, generated files may exist but be inaccessible, or the flag may be readable without exploitation. Verification therefore became part of the vulnerability specification.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.75\textheight,keepaspectratio]{figures/verification.pdf}
	\caption{Verification contexts and checks}
	\label{fig:verification-system}
\end{figure}

Each validation command contains a name, description, context, command string, timeout, expected exit code, expected stdout/stderr conditions, and a \lstinline|must_recover_flag| field. The runner supports three execution contexts.

\begin{table}[htbp]
	\centering
	\begin{tabular}{@{}>{\raggedright\arraybackslash}p{3.5cm}p{5cm}p{5cm}@{}}
		\toprule
		\textbf{Context}              & \textbf{Meaning}                                                                     & \textbf{Typical use}                                   \\
		\midrule
		\lstinline|container_root|    & Run inside the LXC container as root through \lstinline|pct exec|.                   & Service checks, file checks, package checks.           \\
		\addlinespace
		\lstinline|container_student| & Run inside the LXC container as the \lstinline|student| user.                        & Flag-protection checks from the learner's perspective. \\
		\addlinespace
		\lstinline|external_http|     & Run from the Proxmox host against the container IP, normally using \lstinline|curl|. & Web application health checks and exploit checks.      \\
		\bottomrule
	\end{tabular}
	\caption{Verification runner contexts}
	\label{tab:verification-runner-context}
\end{table}

The validator treats generated validation commands as untrusted. Host-control commands such as \lstinline|pct|, \lstinline|pvesh|, and \lstinline|qm| are rejected, alongside cloud metadata access, OpenRouter/API key references, SSH commands, and external HTTP checks that do not target the generated URL or IP. This is a pragmatic compromise: the model can describe how the challenge should be validated, but the platform constrains where and how the checks can run.

\subsection{Tutor design}\label{sec:tutor}

The tutor is a challenge-aware assistant rather than a general chatbot. When a user sends a message, the chat route loads the authenticated user's active challenge and checks that the supplied challenge ID matches it. It then builds a system prompt containing the challenge title, description, category, difficulty, hint, attack vector, and private solution summary.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.75\textheight,keepaspectratio]{figures/tutor_chat_flow.pdf}
	\caption{Tutor chat flow}
	\label{fig:tutor-chat-flow}
\end{figure}

The tutor's purpose is to provide progressive guidance. It should explain concepts and suggest methods, but it should not reveal the flag or provide the full exploit path in one response. The design uses two layers of protection. First, the tutor system prompt instructs the model not to reveal the flag, exact flag path, or full step-by-step solution. Secondly, the application checks the generated response before streaming it back. If the response contains a \lstinline|FLAG{...}| pattern, the exact stored flag, or the full normalised solution summary, the response is replaced by a block message asking the user to request a smaller hint.

Messages are persisted after a complete assistant response. This supports continuity during an active challenge and enables read-only review in the history page after a challenge has ended.

\subsection{Challenge history and learning review}\label{sec:challenge-history}

The history page increases the educational value of the platform beyond a single active challenge. The history API returns previous challenges for the authenticated user, with message counts and status information.


Completed challenges include the solution summary for learning review. Active challenges do not expose it. This creates a distinction between guidance during an attempt and explanation after a successful solve. It also makes the tutor conversation part of the learning record rather than a temporary front-end-only state.

\subsection{Evaluation harness design}\label{sec:evaluation-harness-design}

The evaluation harness was designed to provide evidence about the whole generated challenge lifecycle rather than only about the final user interface. A normal manual demonstration can show that one challenge works, but it cannot easily show whether generation, deployment, injection, verification, and cleanup behave reliably across different categories and difficulty levels. The harness therefore acts as a repeatable experimental driver for the same core modules used by the application.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.82\textheight,keepaspectratio]{figures/evaluation_harness.pdf}
	\caption{Evaluation harness workflow}
	\label{fig:evaluation-harness-design}
\end{figure}

The harness separates evaluation into four modes, shown in Table~\ref{tab:evaluation-modes}. This separation was important because not every failure has the same meaning. A static generation failure indicates a problem with model output, schema validation, policy validation, or prompt constraints. A deployment failure indicates an infrastructure or orchestration problem. An injection failure often indicates that the generated specification cannot be realised inside the container. A verification failure may indicate either a broken challenge or a brittle generated check. Separating the stages makes it possible to analyse where reliability is lost.

\begin{table}[htbp]
	\centering
	\begin{tabular}{@{}p{2.4cm}p{10.7cm}@{}}
		\toprule
		\textbf{Mode}      & \textbf{Purpose}                                                                                                                                                                                             \\
		\midrule
		\lstinline|static| & Generates and validates vulnerability specifications without creating a container. This isolates \gls{llm} and prompt reliability from infrastructure reliability.                                           \\
		\addlinespace
		\lstinline|deploy| & Creates and destroys a blank container. This tests Proxmox, Ansible, static IP assignment, SSH key injection, and cleanup independently from generated vulnerabilities.                                      \\
		\addlinespace
		\lstinline|inject| & Generates a specification, deploys a container, injects the generated files and commands, and runs non-destructive health and flag-protection checks. This matches the normal launch-time verification path. \\
		\addlinespace
		\lstinline|full|   & Runs the complete lifecycle including generated exploit checks. This gives stronger evidence that the generated vulnerability is solvable, but is slower and can involve state-changing checks.              \\
		\bottomrule
	\end{tabular}
	\caption{Evaluation harness modes}
	\label{tab:evaluation-modes}
\end{table}

Each run records both stage outcomes and evidence for later analysis: generated title, attack vector, package/file/service counts, validation-check counts, a hash of the generated file set, stage durations, verification results, cleanup result, and a failure classification. The file-set hash gives a compact way to compare generated artefacts without relying only on titles or descriptions. The failure classification is deliberately heuristic rather than authoritative; it supports analysis by grouping likely generation, infrastructure, validation-test, timing, and uncertain semantic failures, but individual failures can still require manual inspection.

The design choice to call the same generation, deployment, injection, verification, and cleanup modules as the application was deliberate. It means the evaluation measures the implemented pipeline rather than a separate mock implementation. The trade-off is that full evaluation is slower, depends on the Proxmox host, and can be affected by external infrastructure conditions. This is acceptable because infrastructure reliability is part of the practical feasibility of an on-demand cyber range.

\subsection{Authentication, settings, and user state}\label{sec:auth-settings}

Authentication is implemented with email/password accounts. Passwords are hashed with bcrypt before storage. A successful login creates a session row and sets an HTTP-only cookie named \lstinline|session_token|. The cookie is marked secure in production and has a seven-day expiry. API routes that require login call \lstinline|requireAuth()|, which reads the cookie, checks that the session exists and has not expired, and loads the corresponding user.

The settings route allows the user to update their SSH public key and password. SSH key input is validated with a regular expression that accepts common public key types, including \lstinline|ssh-ed25519|, \lstinline|ssh-rsa|, ECDSA keys, and security-key-backed Ed25519 keys. The launch route refuses to provision a challenge if the authenticated user has not stored an SSH public key. This moves key configuration failure to the start of the workflow, before any LLM call or container creation occurs.

\subsection{Database repositories and status transitions}\label{sec:database-repositories}

Repository modules wrap database access for users, sessions, challenges, and messages. This prevents API routes from containing raw SQL and gives the application a single place to enforce domain behaviour.

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.82\textheight,keepaspectratio]{images/db-repositories.png}
	\caption{Database repository structure}
	\label{fig:db-repositories}

The challenge repository creates new challenges with \lstinline|status = 'active'|, an expiry time one hour after creation, and no \lstinline|completed_at| timestamp. It provides methods for finding the active challenge for a user, retrieving all challenges for history, finding prior challenges in a category for diversity prompting, finding expired active challenges, and transitioning a challenge into a terminal state.

The one-active-challenge rule is enforced in three layers:
\begin{enumerate}
	\item the launch route checks for an existing active challenge at request start;
	\item the launch route re-checks immediately before database insertion, after the slow generation and provisioning steps;
	\item the database has a partial unique index on active challenges for each user.
\end{enumerate}
The database index is the strongest layer because it handles race conditions that application checks cannot fully prevent.

\subsection{OpenRouter generation implementation}\label{sec:openrouter-implementation}

The generation entry point is \lstinline|generateVulnerability()| in \lstinline|app/lib/openrouter.ts|. It generates a random server-side flag, builds a category-specific prompt, converts the Zod vulnerability schema to JSON Schema, calls OpenRouter with a structured response format, parses the returned JSON, validates it against \lstinline|VulnerabilitySpecSchema|, runs semantic policy validation, and returns the validated specification and flag.

The OpenRouter client is deliberately small. It handles model availability checks and chat completions for generation and tutor calls. A separate fallback helper builds a model chain from environment variables and defaults, removes duplicates, and retries retryable failures. Incomplete responses are treated as retryable because truncated JSON was a practical failure mode during development.

\subsection{Prompt catalogue and diversity implementation}\label{sec:prompt-catalogue}

The prompt implementation evolved from a single prompt file into a catalogue of category modules. The current categories are web server misconfiguration, privilege escalation, SQL injection, insecure file permissions, and web application logic flaws. Each category defines a user-facing label and description, a list of variants, whether it supports themes, and a prompt template.

The prompt builder chooses a variant randomly and, for web categories, chooses an application theme randomly. It also queries previous challenges for the user in the same category and passes recent titles and solution summaries into the prompt as an exclusion list. This is not a mathematical guarantee of uniqueness, but it gives the LLM explicit context about what not to repeat. The evaluation harness can measure diversity more concretely using generated titles, attack vectors, and file-set hashes.

\subsection{Container deployment implementation}\label{sec:container-deployment}

Container deployment is implemented through \lstinline|deploy.yml| and the LXC lifecycle role. The playbook creates an Ubuntu 24.04 unprivileged LXC container with one core, 1024 MB memory, an 8 GB root filesystem, static networking on \lstinline|vmbr0|, and the \lstinline|vulnforge| tag. The IP address is static from the reserved range of 192.168.0.201-192.168.0.249, DHCP would occasionally cause failures. It then starts the container, creates the \lstinline|student| user, injects the user's SSH key, waits for an IP address, and writes a deployment artefact containing the VMID, hostname, IP address, and configuration details.

The TypeScript wrapper executes \lstinline|ansible-playbook| using \lstinline|execFile()| rather than shell interpolation. Extra variables such as the SSH public key are passed as JSON. This reduces shell-injection risk and avoids quoting problems with SSH keys. A key implementation issue was SSH key injection: public keys contain spaces and can include comments, so interpolating them into shell commands is fragile. The final playbook writes the key to a temporary file on the host, uses \lstinline|pct push| to place it into the container as \lstinline|authorized_keys|, and then sets ownership and permissions inside the container.

\subsection{Vulnerability injection implementation}\label{sec:vuln-injection}

The injection boundary is defined inside the \lstinline{VulnerabilitySpec}, with the TypeScript runner writing this spec to a temporary JSON file, then passing it to the \lstinline{inject-vulnerability.yml} plyabook. The playbook does the following:

\begin{enumerate}
	\item Validates inputs such as VMID and the spec file
	\item Loads the JSON spec file
	\item Updates the APT cache so packages are up to date
	\item Installed requested packages from the spec file
	\item Creates a temporary staging directory on the host, this is for files that the LLM has generated that are needed for the vulnerability
	\item Creates the directories that the LLM has specified are needed, this could be the web application directory for example
	\item Copies the files into the specified directories, from the temporary staging directory
	\item Applies any required ownership changes, commonly required for privilege escalation, or privilege misconfiguration
	\item Removes the staging directory
	\item Starts and or enables services
	\item Runs any setup commands required
	\item Performs a final restart on required services to ensure all are running smoothly
\end{enumerate}

When using a staging directory to push files, we have to use \lstinline{pct push} rather than \lstinline{pct exec} as this could cause shell escaping issues where file content may contain quotes, dollar signs or other special characters. These are common in PHP, SQL, HTML and JavaScript code that is commonly copied for web vulneraiblities. Having a staging section means that we can avoid this, however, this does partially come at a increased time cost as they are copied twice, but for smaller scale vulnerabilities, this is negligible.

Furthermore, we restart the services at the end again as during testing, we noticed that some setup commands to enable a site to run, create symlinks or modify configurations require the setup commands to run first, so we do this step again to ensure that the state is as expected. For example, without this, a web server would continue serving default configurations, rather than the intentionally vulnerable ones even though the files are present, by doing this final restart, we can ensure that post setup changes are loaded.

Setup commands run as root inside the container as it is required for some scenarios such as database initialisation, or user group changes. To ensure this does not cause unintentional changes, the model is instructed to express these commands through an array, then the playbook loops through them.

\subsection{Verification Implementation}\label{sec:verification-implementation}

\begin{figure}[htbp]
	\centering
	\includegraphics[width=\linewidth,height=0.82\textheight,keepaspectratio]{figures/verification.pdf}
	\caption{Verification diagram}
	\label{fig:verification-diagram}
\end{figure}

Verification is implemented with the \lstinline{verifyInjectedChallenge()} method and the \lstinline{verify-vulnerability.yml} playbook. The TypeScript runner checks to see what level of checks to run based on the health mode. \lstinline{health} mode runs the \lstinline{validation.health_checks} and the \lstinline{validation.flag_protection_checks} methods. If we run on \lstinline{full} mode, it also runs the \lstinline{validation.exploit_checks} method. This takes substantially more time, but is largely used during testing to ensure a type of vulnerability works as expctected, but will not run each time a user decides to spin up a machine. As each vulnerability can vary, these checks are generated by the model in a separate prompt, following a custom Zod schema, similar to the vulnerability generation. This is not foolproof, however, it does provide a layer of protection to ensure the vulnerabilityis exploitable by the end user, in the manner that was intended.

Before execution, the runner substitutes values such as \lstinline{TARGET_IP}, \lstinline{VMID}, \lstinline{TARGET_URL} and \lstinline{FLAG}. It will write the checks to a temporary JSON file and then call the verification playbook. The playbook will go through each command, run them, and return the result of the command in JSON. The runner will evaluate the exit codes of the commands, any required stdout / stderr, forbidden stdout strings, and whether the flag was able to be recovered if the \lstinline{must_recover_flag} is true.

As mentioned previously, the health mode check is used during regular launches. If any of these fail, then the launch route will destroy the container and return an error instead of writing a challenge to the database. Full mode verification is optionally used, often during evaluation. Another reason why we do not use it during regular launches is that some of the exploit checks can mutate the state of the machine, for example, when testing it may alter \lstinline{etc/passwd}, and having that in the users container would damage the integrity of the challenge. To partially mitigate this, there is a desposable 'verifier' container used, but this 'verifier' container can still end up modifying the challenge contanier.

\subsection{Evaluation harness implementation}\label{sec:evaluation-harness-implementation}

The evaluation harness is implemented in \lstinline|scripts/evaluate.ts|. It is a command-line TypeScript script rather than a Next.js route because it is intended for controlled experiments, not for direct user interaction. It loads the same environment files as the web application using \lstinline|@next/env|, so the evaluation uses the same OpenRouter, Ansible, and Proxmox configuration as the deployed prototype.

The script uses Commander to parse and validate command-line options such as mode, categories, difficulties, number of runs, output directory, and concurrency. From these options it builds a list of evaluation tasks. Each task is executed by \lstinline|runOneEvaluation()|, which records a structured result object and times each stage with a small \lstinline|timeStage()| wrapper. This avoids relying on console logs as the main evidence source; timings and outcomes are written into machine-readable artefacts.

For non-deploy modes, the first stage calls \lstinline|generateVulnerability()|. The validated specification and server-side flag are saved under \lstinline|generated-specs/| so that failed runs can be inspected later. These files are private evaluation artefacts because they contain flags and solution metadata. In container-backed modes, the harness then calls \lstinline|deployContainer()|, \lstinline|injectVulnerability()|, \lstinline|verifyInjectedChallenge()| where appropriate, and \lstinline|destroyContainer()| in a \lstinline|finally| block if a VMID was allocated. This ensures cleanup is attempted even when generation, injection, or verification fails after a container has been created.

The harness writes three main outputs after runs complete: \lstinline|results.json| for complete structured data, \lstinline|results.csv| for spreadsheet analysis, and \lstinline|summary.md| for report-level tables and Mermaid charts. The summary includes overall success, stage pass rates, category and difficulty breakdowns, duration distributions, failure stages, and failure classifications. Outputs are also written serially during long evaluations so that partial results are not lost if a later run fails or the evaluation is interrupted.

Failure classification is implemented by \lstinline|classifyFailedRun()|. It uses the recorded failure stage, error text, verification groups, command exit codes, and flag-recovery evidence to assign triage labels such as \lstinline|generation_schema_failure|, \lstinline|generation_policy_failure|, \lstinline|infrastructure_orchestration_failure|, \lstinline|llm_challenge_configuration_failure|, \lstinline|generated_validation_test_failure|, \lstinline|evaluator_timing_fragility|, or \lstinline|uncertain_semantic_failure|. These labels are not treated as proof; they are a practical way to make the evaluation results interpretable before manual review.

One implementation problem was that early evaluation failures were too coarse. A single failed run could hide whether the model generated invalid JSON, the container failed to start, a service failed after injection, the flag was exposed directly, or the exploit command was simply brittle. The final harness addresses this by preserving command results, validation groups, stage timings, and classification reasons. This made the Results and Evaluation chapter possible because failures could be discussed by cause rather than only as a total failure count.

\subsection{Challenge Launch Implementation}\label{sec:challenge-launch_implementation}

The launch route is located in \lstinline{app/api/challenge/launch/route.ts}. It uses server sent events to continually update the user as to the state of the challenge whilst it is being created. Authentication, SSH key validation, active challenge checks, and request validation occur before we being the stream to the user. Once the user has selected a type of challenge, and difficulty, and we have done all the verification on the backend, the stream begins, and the user receives progress and errors relating to the challenge.

The progress messages relate to generation, verficiation, deployment, injection, and health verification. On success, it returns the challenge object with the SSH command the user would use, on failure, it attempts to destroy the container, and returns an error message to the user. It also handles a race condition, as generation and injection can take a while, the route checks again for an active challenge immediately before inserting a new challenge. If there is another challenge which has been inserted into the database, the duplicate is cleaned up.

This route also handles stale active challenges. If an existing active challenge is past the expiration time, the launch route firstly attempts to destroy it and marks the challenge as incomplete before the user continues. This avoids stopping a user from creating a new challenge if a previously expired one is just left without being cleaned up for whatever reaosn.

\subsection{Flag submission and cleanup}\label{sec:flag-submission-and-cleanup}
Flag submission occurse through the route \lstinline{app/api/challenge/submit-flag/route.ts}. This route validates the request body (including checking if the user / request is authenticated), checks the challenge exists and belongs to the current user, verifies that it is still active, and compares the submitted flag to the stored flag. If it is correct, the challenge is marked as complete, and the challenge is destroyed.

The delete route is located in \lstinline{app/api/challenges/[id]/route.ts}. It requires the same authentication as before, marks the challenge as destroyed, and asynchronously invokes the container destruction. This is to help make sure the UI is responsive, even if the container deletion is slow for whatever reason. The TTL reaper on the Proxmox host is still present, acting as a safety net for infrastructure cleanup.

\subsection{Logging}\label{sec:logging}

VulnForge uses Pino for logging. Methods emit structured events based on their names (e.g. \lstinline{challenge.launch_start}). This helps identify any launch failures as we can trace it to the exact method that fails. We ensure to sanitise sensitive fields, for example, \lstinline{password},\lstinline{flag}, \lstinline{token} and other keywords are recursively redacted before being passed into Pino.

\begin{listing}[htbp]
	\begin{minted}{TypeScript}
    function sanitize(value: unknown, seen: WeakSet<object> = new WeakSet(), depth = 0): unknown {
  if (value instanceof Error) {
    return {
      name: value.name,
      message: value.message,
      stack: process.env.NODE_ENV === "development" ? value.stack : undefined,
    };
  }

  if (!value || typeof value !== "object") return value;

  if (seen.has(value)) return "[circular]";
  if (depth >= MAX_SANITIZE_DEPTH) return "[max-depth-exceeded]";

  seen.add(value);

  try {
    if (Array.isArray(value)) {
      return value.map((nestedValue) => sanitize(nestedValue, seen, depth + 1));
    }

    const result: LogFields = {};
    for (const [key, nestedValue] of Object.entries(value)) {
      if (isSensitiveField(key)) {
        result[key] = "[redacted]";
      } else {
        result[key] = sanitize(nestedValue, seen, depth + 1);
      }
    }
    return result;
  } finally {
    seen.delete(value);
  }
}
	\end{minted}
	\caption{Recursive implementation of sanitising logs}
	\label{lst:recursive-logs}
\end{listing}

The above method is the recursive one used for safe logging. It walks through the fields passed in, primitive and undefined values are returned unchanged. Error objects are converted into more concise objects, with extra information such as stack traces. For arrays, the method calls itself on each element, replacing the value with \lstinline{"[redacted]"}, including nested values. To protect itself from unsafe recursion, we use a \lstinline{WeakSet} which stores objects currently being visited, and if there are duplicates, it returns \lstinline{"[circular]"} to stop infinite recursion. There is also a max depth limit, currently 25, that leads to the function returning \lstinline{"[max-depth-exceeded]"}.

\section{Design evolution and implementation problems}\label{sec:implementation-problems}

\subsection{Structured LLM output}\label{sec:llm-output}

Initially, we just asked the model to generate a set of files and commands to run on the container, then attempted to execute them, but it soon became clear that this was unsafe, difficult to debug, and often failed. Instead, we moved towards the strucutred specification that the model must follow, with validation from Zod, parsing the JSON and policy validation to have a sort of 'contract' with the model. This made the responses much more reliable, and made it much easier to inject, verify and evaluate the vulnerability, without having to redesign the entire application.

\subsection{Model generated flags to server side flags}\label{sec:flag-generation}

We started with the model generating the flag during injection, but this led to an issue. When we log the machine and vulnerability, Ansible needs the flag, however, when the LLM would embed it in something other than a file, for example in a database for a SQL injection, it would struggle to retrieve the flag. So instead, we generate the flag server side, and prompt the model to embed this exact value. This makes the format more reliable, however, we must verify the model embeds the exact flag we provided. To do this, we have schema and policy validation in the LLMs response, flag protection checks and optional full verification checks which ensures the exact flag is embedded as described.

\subsection{Streaming progress}\label{sec:streaming-progress}

The container provisioning, and LLM generation were quite slow when we started. It started off as a syncrhonous task, and displayed to the user as so, but it soon became apparent this was too slow. The launch route instead moved to server sent events, making the long launches more understanble from the users perspective as it progresses from deployment, injection, and verification.

\subsection{In memory tutor state to persisted messages}\label{sec:tutor-state}

We started off with an in memory chat that was just used in the individual challenge. However, this did harm the learning process when the page refreshes as you would lose the past messages. It also prevented you from reflecting on past messages. Instead, storing them in the database meant we could save them when the user refreshes, and also in the history page. This supports the continuity of learning during and after the attempt, making it a record of learning rather than just as assistant.

\section{Summary}\label{sec:summary}

The final implementation satisfies the core aim of the project: it can generate an LLM authored vulnerability specification, provision an isolated LXC container, inject generated artefacts, verify the challenge's basic health and flag protection, expose the environment to the user through SSH, support guided tutor interaction, and record the attempt in challenge history. The most important design decision is the structured specification boundary between the LLM and the infrastructure. This boundary makes the system extensible because new categories, verification checks, and evaluation modes can be added without giving the model direct control over the host.

The main remaining limitations are also clear. Full exploit verification is optional and slower because it requires a disposable verifier container. The deployment networking model is assumed rather than fully automated in the application. Finally, a production-grade deployment would need further hardening and immediate cleanup after successful completion. These limitations are considered again in the evaluation and reflection chapters.
