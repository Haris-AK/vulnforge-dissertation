This chapter reflects on the transferable learning from the project. It focuses less on individual technical skills and more on how VulnForge changed the assumptions I used to make design, implementation, and evaluation decisions.

\section{Critical narrative of the experience}\label{sec:challenges}

At the start of the project, I treated VulnForge mainly as an integration problem. My assumption was that the main difficulty would be connecting a web interface, an \gls{llm}, Ansible, and Proxmox so that a learner could request a vulnerable container. That assumption was too narrow. The harder problem was deciding whether an automatically generated challenge was safe, usable, educationally meaningful, and reliable enough to expose to a learner.

The first major change in thinking concerned \gls{llm} output. I initially viewed prompt design as the main control mechanism: if the prompt was specific enough, the model would produce usable files and commands. In practice, generated output could be malformed, unsafe, incomplete, plausible but wrong, or valid in structure but unsuitable for the intended category. The design therefore moved from free-form generation towards a structured vulnerability specification validated by Zod and policy checks. This changed my assumption from ``the model authors the challenge'' to ``the model proposes data that the platform may accept, reject, or verify''.

Flag handling produced a similar shift. Allowing the model to invent or manage the flag seemed convenient, but it blurred ownership of the most important secret in the system. Generating the flag server-side created a clearer boundary: deterministic application code owns the secret, while the generated specification creates the route to it. This became a broader design lesson. In a security-sensitive system, critical authority should remain with trusted application logic wherever possible.

Verification changed my view of what it means for the system to work. At first, a successful Ansible run seemed like strong evidence that a challenge had been created. Evaluation showed that this was insufficient. A container could deploy while the service served the wrong content, a file could exist with wrong permissions, or the flag could be readable directly by the \lstinline|student| user. This led to separate health checks, flag-protection checks, and full exploit verification. It also showed that generated validation commands are themselves untrusted artefacts. A failed exploit check may mean the challenge is broken, but it may also mean the generated check is too strict or brittle. Evaluation therefore became a diagnostic process rather than a simple pass/fail judgement.

Infrastructure failures also challenged my assumptions. I initially treated networking as background support, but rapid container creation exposed address allocation and capacity problems. Some failures had nothing to do with the generated challenge. This taught me that, in a cyber range style project, infrastructure is part of the system being evaluated. Its failures must be recorded and separated from generation, injection, and verification failures.

\section{Analysis and application}\label{sec:reflection}

The main double-loop learning from the project is a changed definition of reliability. Before the project, I would have treated reliability mostly as a property of the code I wrote: if the TypeScript compiled, the routes behaved correctly, and the playbooks ran, then the system was reliable. VulnForge showed that this is too limited when the system depends on generated specifications, generated files, generated commands, and generated checks. Reliability is a property of the whole pipeline and of the boundaries between trusted and untrusted components.

This led to a more defensive architecture. The \gls{llm} is valuable because it can create varied scenarios, but it should not be trusted with direct control over infrastructure. The schema, policy validator, server-side flag generation, restricted verification contexts, launch checks, and tutor leakage filters all apply the same principle: generative components should be constrained by deterministic components. This lesson transfers beyond VulnForge. In future AI-assisted systems, I would define contracts, validators, fallback behaviour, and failure categories before relying on generated output.

The project also changed how I think about tests. I began with the assumption that tests mainly demonstrate success. The evaluation harness became more useful when it explained failure. Separating generation failures, deployment failures, injection failures, flag-protection failures, exploit-check failures, and cleanup results made the findings interpretable. A single overall failure rate would hide important information, because each failure type implies a different improvement.

Another changed assumption concerned educational value. It is tempting to treat a challenge as successful if the learner can obtain the flag. VulnForge showed that exploitability alone is not enough. The flag must not be exposed trivially, the tutor must not reveal the solution, the challenge must be understandable, and the container must not remain available indefinitely. The system therefore has competing requirements: it must be vulnerable enough to support learning, constrained enough to reduce risk, and guided enough to help without removing investigation.

I also learned the value of explicit state. Challenge statuses, one-active-challenge enforcement, expiry handling, history pages, logs, and cleanup were not just implementation details. They made the lifecycle understandable. In systems involving asynchronous infrastructure and generated content, hidden state causes confusion. Explicit state made it easier to reason about races, stale challenges, expired containers, and failed cleanup.

\section{Implications for future practice}\label{sec:implications}

In future projects, I would identify core assumptions earlier and test them with small experiments. For VulnForge, assumptions such as ``the model will follow the schema'', ``Ansible success implies usability'', ``the network will allocate addresses reliably'', and ``a generated exploit check proves exploitability'' all needed to be challenged sooner.

I would also build evaluation infrastructure earlier. The harness was valuable because it exposed stages, timings, artefacts, and failure reasons. It should have been treated as part of the architecture rather than as a final reporting tool. Earlier evaluation would have made reliability problems visible before other features depended on them.

A second transferable lesson is to separate generated content from trusted control paths. Generated text, code, commands, tests, and tutor responses should be treated as untrusted inputs. They can be useful, but they need contracts, validation, sandboxing, logging, and controlled execution contexts. This is especially important in cyber security projects, where both users and generated artefacts may behave adversarially.

If I were starting VulnForge again, I would keep the same central architecture, but I would make three decisions earlier: define the vulnerability specification and policy validator before expanding challenge categories, use controlled networking before large-scale evaluation, and design the verification harness before relying on generated challenges in the user interface. These changes would not remove the uncertainty of \gls{llm}-generated content, but they would reduce hidden assumptions.

Overall, the project taught me that the central challenge was not mastering a specific framework or tool. The transferable learning was about engineering under uncertainty: constraining untrusted generation, classifying failure, making lifecycle state explicit, and balancing educational usefulness against security and operational risk.
